<Aside type="caution" title="Required dependency">
PostgreSQL is a **required dependency** for OpenGateLLM to run.
</Aside>

OpenGateLLM uses PostgreSQL as its primary relational database. It has **two** main purposes:
- **Ressources reference**: store and manage the application resources (roles, organizations, users, permissions, api keys, models, collections, documents)
- **Usage monitoring**: track API requests with metrics (tokens, costs, duration, carbon footprint...)

Check the schema of the database in the [`models.py`](https://github.com/etalab-ia/OpenGateLLM/blob/main/api/sql/models.py) file.

</FileTree>

## Configuration


To configure the PostgreSQL dependency, you need to add the database connection information in the `dependencies` section of your `config.yml` file.  
Check [Postgres section](/configuration/configuration_file/#postgresdependency) in configuration file documentation for more information.

Example:
```yaml
dependencies:
    [...]
    postgres:
        url: postgresql+asyncpg://${POSTGRES_USER:-postgres}:${POSTGRES_PASSWORD:-changeme}@${POSTGRES_HOST:-localhost}:${POSTGRES_PORT:-5432}/postgres
        echo: false
        pool_size: 5
        connect_args:
        server_settings:
            statement_timeout: "120s"
        command_timeout: 60
```


The PostgreSQL dependency accepts all parameters from the [SQLAlchemy AsyncEngine](https://docs.sqlalchemy.org/en/20/core/engines.html#sqlalchemy.create_engine). Only `url` parameter is required.
The connection URL must use the `postgresql+asyncpg://` driver. If you provide a standard `postgresql://` URL, it will be automatically converted to use asyncpg.

## Database Migrations

OpenGateLLM uses [Alembic](https://alembic.sqlalchemy.org/) for database migrations. The API image contains them, but the API does not run them when it starts: a deployment runs them once, with the same image, before starting the API containers. Several API containers starting together would otherwise race on the migration, and a failing migration would keep each of them restarting in a loop.

With Docker Compose, the `db-migrate` service of [`compose.example.yml`](https://github.com/etalab-ia/OpenGateLLM/blob/main/compose.example.yml) does it: the `api` service waits for it, and does not start if it fails.

To upgrade a running instance, run the migrations as their own step:

```bash
docker compose pull && docker compose run --rm db-migrate && docker compose up --detach --wait
```

A single `docker compose up` replaces the running `api` container before the migrations end: if they fail, the new container stays stopped and the API is down. With `docker compose run`, a failure leaves the running API untouched.

Without Docker Compose, run this command before starting the API containers:

```bash
docker run --rm --network <network of postgres> -v ./config.yml:/config.yml:ro ghcr.io/etalab-ia/opengatellm/api:<version> python -m alembic -c api/alembic.ini upgrade head
```

<Aside type="caution" title="Do not skip this step">
The API also starts on a schema that is not up to date: its requests then fail on the missing columns or tables.
</Aside>

For contributing to the database schema, you can follow the instructions in [SQL contributions guide](/contributing/sql/).
