# ADR — Extract RAG into OpenGateRAG (OGR)

* **Status:** Accepted
* **Date:** 2026-07-01
* **Authors:** OpenGateLLM Team
* **Related:**
  * [#924 — Split OpenGateLLM and OpenGateRAG](https://github.com/etalab-ia/OpenGateLLM/issues/924)
  * [#956 — feat(rag): remove rag](https://github.com/etalab-ia/OpenGateLLM/pull/956)
  * [OpenGateRAG](https://github.com/etalab-ia/OpenGateRAG) (release [`0.1.0`](https://github.com/etalab-ia/OpenGateRAG/releases/tag/0.1.0))
* **Decision Outcome:** Extract the RAG building block from OpenGateLLM (OGL) into a separate service, [OpenGateRAG (OGR)](https://github.com/etalab-ia/OpenGateRAG), in two stages (soft then hard separation), and refocus OGL on inference, governance, and the admin console.

**Progress:** soft separation and hard separation are implemented. Remaining follow-ups: Redis cache on the OGL identity precall, removal of the deprecated search-tool bridge, and dropping leftover RAG tables from the OGL schema after data has been copied.

---

## Context

OpenGateLLM is positioned and implemented as a **sovereign, open-source inference gateway**. Its product core is not RAG, but exposing, governing, and operating generative AI models:

- inference endpoints: `/v1/chat/completions`, `/v1/embeddings`, `/v1/rerank`, `/v1/ocr`, `/v1/audio/transcriptions`;
- administration: users, roles, API keys, organizations, routers, providers;
- governance: rate limits per role/router, user budget, priority, usage, costs, metrics, and carbon footprint;
- Playground: admin console and chat page, with no document-management UI.

Historically, OGL also shipped an optional RAG stack (Elasticsearch + embedding model), exposing `/v1/collections`, `/v1/documents`, `/v1/search`, `/v1/chunks`, `/v1/parse`, and a search tool integrated into `/v1/chat/completions` (`tools: [{ "type": "search", ... }]`).

Keeping that stack inside OGL raised several issues:

**Maintainability and operations.** Elasticsearch scalability, index management, document ingestion, and storage quotas belong to a product and operational domain distinct from the inference gateway.

**Product positioning.** RAG was initially meant as a skills-building aid and an API for integrators, not as a full RAG product comparable to specialized market offerings. The Playground also provided no UI for collections, documents, or search.

**API debt and legacy.** Document endpoints evolved through successive iterations (aliases, deprecated endpoints, legacy fields), which blurred the public contract and made extraction harder.

**Goal.** Refocus OGL on inference, governance, and the admin console, while giving RAG its own technical and product trajectory.

## Decision

| # | Decision | Status |
|---|---|---|
| 1 | **Extract the RAG building block** into a dedicated service: [OpenGateRAG (OGR)](https://github.com/etalab-ia/OpenGateRAG) | ✅ Done |
| 2 | **Deploy OGR as a distinct service** (not an optional OGL dependency), with a reverse proxy for a unified user-facing API when desired | ✅ Done |
| 3 | **Migrate in two stages**: soft separation (shared database), then hard separation (independent databases) | Soft ✅ / Hard ✅ |
| 4 | **Make OGR depend on OGL for identity and model access**: OGR does not manage its own tokens natively; every endpoint authenticates via a call to OGL | ✅ Explicit auth / ⏳ Redis cache |
| 5 | **Deprecate the search tool** embedded in `/v1/chat/completions` in `v0.5.0`, then **remove** it in `v1.0.0` | ⏳ In progress (`search_opengaterag_url` deprecated) |
| 6 | **Remove the public `/v1/parse` endpoint** from OGL; parsing becomes an internal OGR capability (ingestion) | ✅ Done |

### Alternatives considered

| Option | Description | Decision |
|---|---|---|
| A | OGR as an **OGL dependency**: enabling it turns on RAG endpoints within the same API | Rejected |
| B | OGR as a **distinct service**, with a reverse proxy to offer a unified user-facing API | Selected |

Option A did not allow dedicated RAG resources, separate Elasticsearch ownership, or an autonomous RAG product trajectory. Option B was selected.

### Target scope

**OGR** owns document and search features (routers: `collections`, `documents`, `search`):

- collections and documents, stored in the OGR Postgres database;
- chunks under `/v1/documents/{document_id}/chunks` (no dedicated `/v1/chunks` router); chunk text, embeddings, and metadata live in Elasticsearch, not in Postgres;
- document parsing and ingestion (internal to upload, via `ParserManager`);
- lexical, semantic, and hybrid search;
- document quotas (`user.storage_limit`) and the RAG permission `user.create_public_collection`.

**OGL** keeps generic inference capabilities:

- `/v1/embeddings` stays in OGL (OGR uses it to vectorize, with the client API key);
- `/v1/rerank` stays in OGL (external RAG pipelines may use it);
- `/v1/chat/completions` stays in OGL; the search tool is now only an optional HTTP bridge to OGR, and is destined to be removed;
- `/v1/ocr` and `/v1/audio/transcriptions` stay in OGL as long as they are treated as inference / multimodality endpoints, not as an OGR document pipeline;
- identity, tokens, roles, organizations, routers, providers, usage, and the Playground stay in OGL.

### Authentication model

OGR does not manage its own tokens natively. It relies on OGL to validate identity, and to access models (embeddings, etc.).

**Principle:** authentication does not rely on a side effect of an embedding call. Every protected OGR endpoint goes through an `AccessController` that calls OGL before business logic.

**Implemented (hard separation):**

- On every authenticated request, OGR calls `GET {OPENGATELLM_URL}/v1/me/info` with the client Bearer token ([`_accesscontroller.py`](https://github.com/etalab-ia/OpenGateRAG/blob/main/opengaterag/api/helpers/_accesscontroller.py)).
- OGR stores only `user_id` (the OGL user `id`) and the API key in `RequestContext`. RAG rights are **not** read from the OGL payload.
- Model calls (e.g. `/v1/embeddings`) reuse the same client API key toward OGL.
- OGR uses its **own** Postgres database (`dependencies.postgres.url` in the OGR config). It no longer reads `OPENGATELLM_DATABASE_URL` / the OGL schema.

**Not implemented yet:** a Redis cache on the `/v1/me/info` precall (TTL, invalidation, behavior when OGL is unavailable).

### Data ownership after hard separation

OGR Alembic (`opengaterag/api/alembic`, initial revision `3c24be6d0557`) owns the RAG schema. Container startup runs `alembic upgrade head` before Gunicorn.

| OGR table | Columns | Notes |
|---|---|---|
| `user` | `id`, `create_public_collection`, `storage_limit`, `created`, `updated` | `id` **is** the OGL user id (no `ogl_user_id` column). Missing users are upserted on first collection create, with `storage_default_limit`. |
| `organization` | `id`, `name`, `created`, `updated` | Present in the OGR schema; not referenced by OGR `user` and unused by application code today. |
| `collection` | `id`, `user_id`, `name`, `description`, `visibility`, `created`, `updated` | Visibility enum `collectionvisibility` (`PRIVATE` / `PUBLIC`). |
| `document` | `id`, `collection_id`, `name`, `size`, `created` | `size` is token consumption, not raw file bytes. |

**Actual decisions that differ from the original hard-separation sketch:**

- There is no `ogl_user_id`. Collection ownership and `/v1/me/info` both use the OGL numeric user id as `user.id`. Preserving those ids during migration is mandatory so Elasticsearch `collection_id` / `document_id` keep matching Postgres.
- `storage_limit` moved from the OGL **role** to the OGR **user** (one value per user, copied from the user's role at migration time).
- `create_public_collection` moved from an OGL role permission to an OGR user boolean. There is no OGR `/v1/users/permissions` API yet; operators can `UPDATE "user" SET create_public_collection = true` (or wait for a later admin surface).
- Elasticsearch remains the vector store. The SQL migration does **not** copy chunks, embeddings, or chunk metadata.

OGL still authenticates users and may still contain leftover `collection` / `document` tables plus `role.storage_limit` until a follow-up OGL Alembic drop. The OGL ORM no longer maps those document tables. `create_public_collection` has been removed from OGL `PermissionType` and from the Playground role form.

### Migration plan

#### Stage 1 — Soft separation (shared database) ✅ Done

- RAG code extracted into [OpenGateRAG](https://github.com/etalab-ia/OpenGateRAG) (release `0.1.0`).
- Document endpoints removed from OGL ([#956](https://github.com/etalab-ia/OpenGateLLM/pull/956)).
- OGL and OGR pointed at the same database (`OPENGATELLM_DATABASE_URL`).
- SQL schemas remained orchestrated by the OGL repository.
- Explicit auth: every OGR endpoint calls `GET {OPENGATELLM_URL}/v1/me/info` before business logic.
- The `collection` and `document` tables remained in the OGL schema to avoid a data migration at kickoff.
- When enabled (`search_opengaterag_url`), the OGL search tool calls `POST {OGR}/v1/search` instead of local search.
- OGR merges OGL + OGR OpenAPI documentation.

**Observed benefits**

- No data migration at kickoff.
- User deletion still propagated by existing SQL constraints.
- Application separation delivered before full data separation.

**Limits of that stage (now addressed by stage 2)**

- OGR depended on the OGL SQL schema.
- OGL still held document tables that are no longer part of its product core.
- Permissions such as `create_public_collection` and the `storage_limit` cap remained on OGL roles / Playground.

#### Stage 2 — Hard separation (independent databases) ✅ Done

- OGR has a dedicated Postgres database and its own Alembic migrations.
- OGR config uses `dependencies.postgres.url` (see `config.example.yml` / `compose.example.yml`); `OPENGATELLM_DATABASE_URL` is gone.
- Document quotas and `create_public_collection` are stored on OGR `user`.
- Collections, documents, and RAG user fields are copied with [`adr/scripts/2026-07-01-split-rag-migrate.py`](scripts/2026-07-01-split-rag-migrate.py) (see [Migration script](#migration-script)).
- Elasticsearch is unchanged: keep the existing cluster and **index name** so chunk ids keep matching migrated Postgres ids.

**Still to do after the database split**

- Optionally add OGR permission-management endpoints (e.g. `/v1/users/permissions`).
- Add a Redis cache on the `/v1/me/info` precall (TTL, invalidation).
- Remove the search-tool bridge from OGL (`search_opengaterag_url` and related helper) by `v1.0.0` at the latest.
- After a successful copy and cutover, drop leftover `collection` / `document` tables and `role.storage_limit` from the OGL schema.

### Impacted features

**Search tool in `/v1/chat/completions`.** Local coupling is gone. An optional HTTP bridge to OGR remains (`search_opengaterag_url`, already deprecated). Trajectory: documented deprecation in `v0.5.0`, removal in `v1.0.0`. Integrators will compose OGR (search) then OGL (chat), or use a unified reverse proxy.

**RAG permissions.** `create_public_collection` is owned by OGR (`user.create_public_collection`). It is no longer an OGL Playground permission. Until an OGR admin API exists, set it in the OGR database.

**OpenAPI documentation.** OGR already merges OGL + OGR specs into a unified view.

**Storage limit.** Owned by OGR per user (`user.storage_limit`). New OGR users created at first collection insert receive `settings.storage_default_limit` (unlimited when null).

**OGR administration.** No OGR admin UI is planned short term. A dedicated Playground may be considered later.

## Consequences

### Positive

- OGL can deploy without Elasticsearch or a document stack (“gateway only”).
- OGR can evolve, scale, and version independently ([OGR releases](https://github.com/etalab-ia/OpenGateRAG/releases)), including its own Postgres and Alembic.
- OGL’s API contract is refocused on inference and governance.
- A reverse proxy (and OGR’s OpenAPI merge) keeps a unified API option.

### Negative / risks

- Two services (and now two Postgres databases) to operate, monitor, and document for a full deployment.
- Every OGR request currently depends on a synchronous round-trip to OGL (`/v1/me/info`); without a cache, OGR latency and availability are tied to OGL.
- Upcoming breaking change for search-tool clients (setting already deprecated; removal planned in `v1.0.0`).
- Hard split is a **one-shot copy**, not dual-write: RAG writes must be stopped during cutover, and users created in OGL after the copy are not synced until they hit OGR (they then get default quota / `create_public_collection = false`).
- Deleting an OGL user no longer cascades to OGR collections; identity is a numeric id with no foreign key across databases.

### Open / to formalize

- Redis cache parameters for `/v1/me/info` (TTL, invalidation, behavior when OGL is unavailable).
- Timeline to remove leftover OGL RAG tables, `role.storage_limit`, leftover `CREATE_PUBLIC_COLLECTION` enum values, and the search-tool bridge.
- Whether OGR should persist organization membership (`organization` is already in the OGR schema but unused).
- OGR admin API to set `create_public_collection` and `storage_limit` without raw SQL.

## Migration script

The [`adr/scripts/2026-07-01-split-rag-migrate.py`](scripts/2026-07-01-split-rag-migrate.py) script copies RAG **Postgres** metadata from an OpenGateLLM database (soft-split / pre-cutover source) to an OpenGateRAG database.

It copies, preserving primary keys:

| Source (OGL) | Destination (OGR) |
|---|---|
| `organization` (`id`, `name`, `created`, `updated`) | `organization` (copied because the table exists; unused by OGR app code today) |
| `user.id` + `user.created` / `user.updated` + `role.storage_limit` + role permission `CREATE_PUBLIC_COLLECTION` | `user` (`id`, `create_public_collection`, `storage_limit`, `created`, `updated`) |
| `collection` | `collection` (same ids, `visibility` mapped onto the OGR enum) |
| `document` | `document` (same ids, including `size`) |

It does **not** copy:

- OGL identity payload (email, password, tokens, roles, routers, usage, …);
- Elasticsearch chunks, embeddings, or chunk metadata;
- files themselves (OGR does not store raw uploads in Postgres).

> [!IMPORTANT]
> Keep Elasticsearch on the **same cluster and index name** used before the split (often `opengatellm` after the 2026-01-30 index consolidation). OGR `config.example.yml` defaults `index_name` to `opengaterag` for **new** installs only. If you change the index name without reindexing, search will not see existing chunks. This script does not reindex Elasticsearch.

The script never `DELETE`s or `DROP`s source data. Re-runs are idempotent (`ON CONFLICT (id) DO NOTHING`). Prefer an empty OGR database created by OGR Alembic.

### Order of operations

1. Provision a **new** Postgres instance (or database) for OGR. Do not reuse the OGL database URL.
2. Run OGR Alembic on that database (`alembic -c opengaterag/api/alembic.ini upgrade head`), or start OGR once so `scripts/startup_api.sh` applies migrations. Confirm tables `user`, `collection`, `document` exist.
3. Point OGR `dependencies.elasticsearch` at the **existing** vector index (same `index_name`, hosts, credentials, vector size).
4. Stop RAG writes: stop OGR, and disable or avoid the OGL search tool (`search_opengaterag_url`) for the window. A short RAG downtime is required; there is no dual-write.
5. Run the migration (dry-run first, then the real copy). See below.
6. Switch OGR `dependencies.postgres.url` to the new database if it was not already, then start OGR.
7. Verify `GET /v1/collections`, document listing, and search against a known collection id.
8. Only after verification, schedule a later OGL Alembic revision to drop leftover `collection` / `document` tables and `role.storage_limit`. Do **not** drop the source tables before the copy.

### How to run

1. Clone the OpenGateLLM repository on the target server (the script lives next to this ADR):

```bash
git clone https://github.com/etalab-ia/OpenGateLLM.git && cd OpenGateLLM
```

2. Install the dependencies

> [!NOTE]
> We recommend to create a virtual environment and activate it before installing the dependencies.

```bash
pip install ".[api]"
```

3. Create the bash script to run the migration

```bash
touch run.sh
```

The script should look like this:

```bash
#!/bin/bash
export PYTHONPATH=.

export SOURCE_POSTGRES_URL=
export DESTINATION_POSTGRES_URL=
export DRY_RUN=false

python adr/scripts/2026-07-01-split-rag-migrate.py > migration.log 2>&1
```

The environment variables are:

| Variable | Description | Example |
|----------|-------------|-------------|
| `SOURCE_POSTGRES_URL` | OpenGateLLM PostgreSQL URL (the database that still holds `collection` / `document`). Use `postgresql+asyncpg://` (a `postgresql://` URL is accepted and converted). | `postgresql+asyncpg://postgres:changeme@localhost:5432/opengatellm` |
| `DESTINATION_POSTGRES_URL` | OpenGateRAG PostgreSQL URL (empty schema after Alembic). Must be a **different** database than the source. | `postgresql+asyncpg://postgres:changeme@localhost:5433/postgres` |
| `DRY_RUN` | If `true`, inspect source/destination and log counts without writing. | `true` |

4. Run the script

1. Dry-run (recommended first): set `DRY_RUN=true` in `run.sh`, then:

    ```bash
    ./run.sh
    ```

    Inspect `migration.log`, then set `DRY_RUN=false` in `run.sh` before the real copy.

2. Without nohup:

    ```bash
    ./run.sh
    ```

3. With nohup to run the script in the background:

    ```bash
    nohup bash ./run.sh > migration.log 2>&1 &
    ```

In all cases, the script will output the progress of the migration to the `migration.log` file. If the real run fails, you can rerun it; existing destination ids are skipped.

5. Check the migration

```bash
cat migration.log
```

Confirm that source and destination counts match for `user`, `collection`, and `document`, and that the sampled sanity check passed. Then exercise OGR search on a collection that had chunks in Elasticsearch.

### Rollback / safety

- The script does not modify the source database. Rolling back the cutover means pointing OGR back at the previous Postgres URL (shared OGL database) **before** dropping OGL RAG tables.
- To undo a failed copy on an otherwise empty OGR database, drop and recreate that database, run OGR Alembic again, then rerun the script.
- Do not point `SOURCE_POSTGRES_URL` and `DESTINATION_POSTGRES_URL` at the same database; the script aborts in that case.
- After cutover, OGL user deletion no longer removes OGR collections. Clean up OGR rows separately if that is required.
