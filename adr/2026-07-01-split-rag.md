# ADR — Extract RAG into OpenGateRAG (OGR)

* **Status:** In Progress
* **Date:** 2026-07-01
* **Authors:** OpenGateLLM Team
* **Related:**
  * [#924 — Split OpenGateLLM and OpenGateRAG](https://github.com/etalab-ia/OpenGateLLM/issues/924)
  * [#956 — feat(rag): remove rag](https://github.com/etalab-ia/OpenGateLLM/pull/956)
  * [OpenGateRAG](https://github.com/etalab-ia/OpenGateRAG) (release [`0.1.0`](https://github.com/etalab-ia/OpenGateRAG/releases/tag/0.1.0))
* **Decision Outcome:** Extract the RAG building block from OpenGateLLM (OGL) into a separate service, [OpenGateRAG (OGR)](https://github.com/etalab-ia/OpenGateRAG), in two stages (soft then hard separation), and refocus OGL on inference, governance, and the admin console.

**Progress:** soft separation is done. Hard separation (independent databases, document permissions/quotas owned by OGR) remains.

---

## Context

OpenGateLLM is positioned and implemented as a **sovereign, open-source inference gateway**. Its product core is not RAG, but exposing, governing, and operating generative AI models:

- inference endpoints: `/v1/chat/completions`, `/v1/embeddings`, `/v1/rerank`, `/v1/ocr`, `/v1/audio/transcriptions`;
- administration: users, roles, API keys, organizations, routers, providers;
- governance: rate limits per role/router, user budget, priority, usage, costs, metrics, and carbon footprint;
- Playground: admin console and chat page, with no document-management UI.

Historically, OGL also shipped an optional RAG stack (Elasticsearch + embedding model), exposing `/v1/collections`, `/v1/documents`, `/v1/search`, `/v1/chunks`, `/v1/parse`, and a search tool integrated into `/v1/chat/completions` (`tools: [{ "type": "search", ... }]`).

Keeping that stack inside OGL raised several issues:

**Maintainability and operations.** Elasticsearch scalability, index management, document ingestion, and storage quotas belong to a product and operational domain distinct from the inference gateway.

**Product positioning.** RAG was initially meant as a skills-building aid and an API for integrators, not as a full RAG product comparable to specialized market offerings. The Playground also provided no UI for collections, documents, or search.

**API debt and legacy.** Document endpoints evolved through successive iterations (aliases, deprecated endpoints, legacy fields), which blurred the public contract and made extraction harder.

**Goal.** Refocus OGL on inference, governance, and the admin console, while giving RAG its own technical and product trajectory.

## Decision

| # | Decision | Status |
|---|---|---|
| 1 | **Extract the RAG building block** into a dedicated service: [OpenGateRAG (OGR)](https://github.com/etalab-ia/OpenGateRAG) | ✅ Done |
| 2 | **Deploy OGR as a distinct service** (not an optional OGL dependency), with a reverse proxy for a unified user-facing API when desired | ✅ Done |
| 3 | **Migrate in two stages**: soft separation (shared database), then hard separation (independent databases) | Soft ✅ / Hard ⏳ |
| 4 | **Make OGR depend on OGL for identity and model access**: OGR does not manage its own tokens natively; every endpoint authenticates via a call to OGL | ✅ Explicit auth / ⏳ Redis cache |
| 5 | **Deprecate the search tool** embedded in `/v1/chat/completions` in `v0.5.0`, then **remove** it in `v1.0.0` | ⏳ In progress (`search_opengaterag_url` deprecated) |
| 6 | **Remove the public `/v1/parse` endpoint** from OGL; parsing becomes an internal OGR capability (ingestion) | ✅ Done |

### Alternatives considered

| Option | Description | Decision |
|---|---|---|
| A | OGR as an **OGL dependency**: enabling it turns on RAG endpoints within the same API | Rejected |
| B | OGR as a **distinct service**, with a reverse proxy to offer a unified user-facing API | Selected |

Option A did not allow dedicated RAG resources, separate Elasticsearch ownership, or an autonomous RAG product trajectory. Option B was selected.

### Target scope

**OGR** owns document and search features (current routers: `collections`, `documents`, `search`):

- collections and documents;
- chunks under `/v1/documents/{document_id}/chunks` (no dedicated `/v1/chunks` router);
- document parsing and ingestion (internal to upload, via `ParserManager`);
- lexical, semantic, and hybrid search;
- document quotas and permissions (still read from the OGL schema / roles today; to be owned by OGR after hard separation).

**OGL** keeps generic inference capabilities:

- `/v1/embeddings` stays in OGL (OGR uses it to vectorize, with the client API key);
- `/v1/rerank` stays in OGL (external RAG pipelines may use it);
- `/v1/chat/completions` stays in OGL; the search tool is now only an optional HTTP bridge to OGR, and is destined to be removed;
- `/v1/ocr` and `/v1/audio/transcriptions` stay in OGL as long as they are treated as inference / multimodality endpoints, not as an OGR document pipeline.

### Authentication model

OGR does not manage its own tokens natively. It relies on OGL to validate identity and rights, and to access models (embeddings, etc.).

**Principle:** authentication does not rely on a side effect of an embedding call. Every protected OGR endpoint goes through an `AccessController` that calls OGL before business logic.

**Today (soft separation):**

- On every authenticated request, OGR calls `GET {OPENGATELLM_URL}/v1/me/info` with the client Bearer token ([`_accesscontroller.py`](https://github.com/etalab-ia/OpenGateRAG/blob/main/opengaterag/api/helpers/_accesscontroller.py)).
- The response provides `id` and `permissions` (including `create_public_collection`), stored in OGR’s `RequestContext`.
- Model calls (e.g. `/v1/embeddings`) reuse the same client API key toward OGL.
- In parallel, OGR shares the OGL database (`OPENGATELLM_DATABASE_URL`) for document tables and to read role `storage_limit` — data coupling, distinct from the HTTP auth contract.

**Target (hard separation):** keep this precall to `/v1/me/info`, and **add a cache** (Redis) to reduce latency and load on OGL. Document quotas / permissions leave the OGL schema and are owned by OGR.

### Migration plan

#### Stage 1 — Soft separation (shared database) ✅ Done

- RAG code extracted into [OpenGateRAG](https://github.com/etalab-ia/OpenGateRAG) (release `0.1.0`).
- Document endpoints removed from OGL ([#956](https://github.com/etalab-ia/OpenGateLLM/pull/956)).
- OGL and OGR point at the same database (`OPENGATELLM_DATABASE_URL`).
- SQL schemas remain orchestrated by the OGL repository.
- Explicit auth: every OGR endpoint calls `GET {OPENGATELLM_URL}/v1/me/info` before business logic.
- The `collection` and `document` tables remain in the OGL schema to avoid a data migration.
- When enabled (`search_opengaterag_url`), the OGL search tool calls `POST {OGR}/v1/search` instead of local search.
- OGR merges OGL + OGR OpenAPI documentation.

**Observed benefits**

- No data migration at kickoff.
- User deletion still propagated by existing SQL constraints.
- Application separation delivered before full data separation.

**Current limits (transition debt)**

- OGR depends on the OGL SQL schema.
- OGL still holds document tables that are no longer part of its product core.
- Permissions such as `create_public_collection` and the `storage_limit` cap remain on OGL roles / Playground.

#### Stage 2 — Hard separation (independent databases) ⏳ To do

- Create a dedicated OGR database.
- Migrate collections, documents, and metadata from the OGL database to the OGR database.
- Create a `user` table on the OGR side, referencing the OGL user via `ogl_user_id`.
- Move document quotas (`storage_limit`) and RAG permissions (`create_public_collection`) to OGR.
- Optionally add OGR permission-management endpoints (e.g. `/v1/users/permissions`).
- Add a Redis cache on the `/v1/me/info` precall (TTL, invalidation).
- Remove the search-tool bridge from OGL (`search_opengaterag_url` and related helper) by `v1.0.0` at the latest.
- Remove the `collection` / `document` tables and document fields/permissions from the OGL schema and Playground.

### Impacted features

**Search tool in `/v1/chat/completions`.** Local coupling is gone. An optional HTTP bridge to OGR remains (`search_opengaterag_url`, already deprecated). Trajectory: documented deprecation in `v0.5.0`, removal in `v1.0.0`. Integrators will compose OGR (search) then OGL (chat), or use a unified reverse proxy.

**RAG permissions in the Playground.** `create_public_collection` is still exposed on OGL roles, with no collections/documents UI. Remove it from the OGL Playground, or explicitly present it as an OGR permission, at hard separation.

**OpenAPI documentation.** OGR already merges OGL + OGR specs into a unified view.

**Storage limit.** Role-level `storage_limit` in OGL remains tied to the document domain; move it to OGR at hard separation.

**OGR administration.** No OGR admin UI is planned short term. A dedicated Playground may be considered later.

## Consequences

### Positive

- OGL can deploy without Elasticsearch or a document stack (“gateway only”).
- OGR can evolve, scale, and version independently ([OGR releases](https://github.com/etalab-ia/OpenGateRAG/releases)).
- OGL’s API contract is refocused on inference and governance.
- A reverse proxy (and OGR’s OpenAPI merge) keeps a unified API option.

### Negative / risks

- Two services to operate, monitor, and document for a full deployment.
- During soft separation, SQL schema coupling remains strong; hard separation requires a data migration.
- Every OGR request currently depends on a synchronous round-trip to OGL (`/v1/me/info`); without a cache, OGR latency and availability are tied to OGL.
- Upcoming breaking change for search-tool clients (setting already deprecated; removal planned in `v1.0.0`).
- Document permissions and quotas (`create_public_collection`, `storage_limit`) still visible / stored on the OGL side: product ambiguity until they migrate.

### Open / to formalize

- Redis cache parameters for `/v1/me/info` (TTL, invalidation, behavior when OGL is unavailable).
- Timeline to remove document tables, `storage_limit`, `create_public_collection`, and the search-tool bridge from OGL.
- Migration strategy for collections/documents data into the OGR database.
