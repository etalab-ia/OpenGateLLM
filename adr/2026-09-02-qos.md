# Quality of Service (QoS)

Actuellement un système de queueing et de priorisation est implémenté avec Celery et RabbitMQ. Lors du refactoring du endpoint /v1/chat/completions en clean architecture nous allons enlever toute dépendance avec système. **Nous repartons d'une feuille blanche, sans considération du code existant**, avec les objectifs suivants : **protéger chaque provider**, **envoyer au moins chargé**, **aligner le health**.

**L'objectif de cet ADR est donc de définir les principes et la logique de fonctionnement du QoS.** La priorisation des requêtes et le batch feront l'objet d'ADR suivants.

Plusieurs besoins :

1. priorisation : permettre de prioriser certaines requêtes par rapport à d'autres 

    Cela permet d'assurer un traitement des requêtes de certaines clients par rapport à d'autres dans les périodes de fortes charges.

2. qualité de service (QoS): permettre de limiter le nombre de requêtes traité par un provider pour garantir une qualité de service.

    Cela permet 3 choses : 
        - pour les moteurs d'inférence qui ne supportent pas la charge (comme WhisperX), cela évite au modèle de crasher
        - pour les moteurs d'inférence qui supportent la charge (comme vLLM/Mistral), cela permet de fluidifier le traitement des requêtes si le moteur d'inférence n'est pas optimisé pour la charge.
        - permet d'afficher un health cohérent sans se reposer sur l'API du provider

3. batch : permettre d'exécuter des requêtes quand les providers sont disponibles.

    Cela permet de tirer parti des providers tout le long de la journée et de mieux répartir la charge sur les providers pour éviter des saturations.

Ces 3 concepts sont liés. En effet, le batch a besoin d'un indicateur de la charge des providers pour exécuter des requêtes quand ils sont disponibles. La priorisation suppose qu'il existe un mécanisme d'attente pour permettre aux requêtes prioritaires de passer devant les requêtes non prioritaires.

Le QoS répond à ces 2 besoins en définissant 3 niveaux de charge (vert, orange et rouge) et fait attendre les requêtes dans un boucle jusqu'à ce qu'un provider soit disponible. La charge d'un provider peut être mesurée de plusieurs manières : le nombre de requêtes en cours, le poids des fichiers traités par le modèle, tokens in-flight, ...

## Décision

### 1. Une source de charge, trois consommateurs

On compte **nous-mêmes** dans Redis. Pas d’API métriques provider pour l’admission, le least-busy, ni la **saturation** health.

Aujourd’hui le QoS et le least-busy lisent un compteur Redis (`ogl_mg:inflight`) que l’on incrémente au début de la requête et décrémente à la fin (`INCR` / `DECR`). Le **contrôle de limite** et l’**incrément** sont deux allers-retours distincts : deux requêtes peuvent toutes les deux voir « il reste de la place » et entrer. Un crash laisse le compteur trop haut indéfiniment.

On remplace ça par un nombre unique `load(p)` — la charge actuelle du provider `p` et la limite de charge `qos_limit(p)`. Trois mécanismes posent chacun une question différente sur ce même nombre :

| Mécanisme | Question | Condition |
| --- | --- | --- |
| Admission | Cette requête a-t-elle le droit de **démarrer** sur `p` sans dépasser sa capacité ? | `if at least one provider is eligible: load(p)` ≤ `qos_limit(p)` (voir §4) |
| Load balancer (least-busy) | Lequel des providers du router doit prendre la requête ? | `min(load(p) for p in providers)` (voir §5) |
| Saturation health (endpoint /health/models)| À quel point `p` est-il **plein** ? | `load(p) / qos_limit(p)` → vert / orange / rouge (voir §6). |

### 2. Métrique de charge `load(p)` (`inflight`)

Chaque provider a **une** ZSET Redis `ogl_qos:load:{provider_id}`. `load(p)` est le nombre de membres de la ZSET. On ne tient **pas** un entier `INCR` / `DECR` à côté. Ce second chiffre serait une copie de `ZCARD`. Les deux peuvent diverger (crash, `DECR` perdu) — c’est le bug actuel. Compter les membres *est* la charge.

##### 2.1 Les types de métriques de charges

Le type métrique de charge `load(p)` est définie au niveau du router. Nous voulons que tous les providers d'un même routeur soit évaluer sur la base de la même métrique. Dans cet ADR nous nous concentrons sur la métrique `inflight`. Nous ajouterons d'autres métriques ultérieurement (nombre de tokens in-flight, nombre d'audio bytes en cours de traitement, ...).

Le type de métrique est défini au niveau du router.

* **membre** = `request_id` : une requête encore en train de tourner ;
* **score** = date d’expiration du heartbeat (millisecondes), **pas** un rang dans une file ;
* **`load(p)`** = `ZCARD` de cette ZSET, **après** avoir retiré les membres expirés.

#### 2.2 Heartbeat in-flight

##### Le problème

Aujourd’hui : `INCR` au début du forward, `DECR` à la fin. Si le worker crash, si Redis est saturé au `DECR`, ou si le client coupe sans que le `finally` tourne, **personne ne décrémente**. Le compteur reste trop haut jusqu’au `flushdb()` du prochain boot. On sous-admet (voire on bloque tout) alors que le GPU est libre.

Il faut un filet qui n’exige **aucun code après la mort** du process.

##### L’idée

Tant que *cette* requête vit, le worker qui la sert dit à Redis « je suis encore là », en **reculant une date d’expiration** sur le membre. Si les rappels s’arrêtent, cette date passe dans le passé.

Redis **n’efface rien tout seul**. Le prochain script d’admission, en voulant faire entrer quelqu’un, ramasse les membres dont la date est dépassée. Ça s’appelle un heartbeat.

Ce n’est **pas** :

* Redis qui « ping » tout seul ;
* un cron, un worker Celery, un sweeper dédié ;
* un `EXPIRE` sur la clé ZSET (un TTL sur la clé détruirait **toutes** les requêtes du provider d’un coup) ;
* une mesure de la durée du job (un WhisperX de 5 min doit rester dans `load` jusqu’à la fin).

C’est uniquement le filet anti-zombie. La sortie **normale** retire le membre tout de suite, sans attendre les 30 s.

##### Qui

Le **même process FastAPI** (worker gunicorn / uvicorn) qui traite **cette** requête HTTP. Pas un autre service.

Au moment où l’admission réussit, l’adapter Redis démarre une **tâche asyncio à côté** de l’`await forward_request(...)`. Cette tâche vit aussi longtemps que le forward.

```
requête HTTP
  └─ worker FastAPI
       ├─ await forward_request(...)     # peut durer des minutes (WhisperX, vLLM)
       └─ tâche asyncio heartbeat        # toutes les ~10 s : ZADD, jusqu’à la fin du forward
```

##### Quoi, dans Redis

```
ZSET  ogl_qos:load:{provider_id}

  membre = request_id          # quelle requête
  score  = now_ms + 30_000     # morte si plus personne n’écrit d’ici 30 s
```

Exemple, trois requêtes sur le provider 42, `now = 1_000_000` :

| membre | score | lecture |
|---|---|---|
| `req-A` | `1_028_000` | encore 28 s de silence autorisé |
| `req-B` | `1_015_000` | encore 15 s |
| `req-C` | `980_000` | **déjà expiré** (score &lt; now) → zombie à purger |

`load(p)` n’est pas « 3 » tant qu’on n’a pas enlevé `req-C`. Après purge : `ZCARD` = 2.

##### Comment on écrit

**Admission** (Lua, une fois) :

```
ZADD ogl_qos:load:{provider_id}  {now_ms + 30_000}  {request_id}
```

**Heartbeat** (tâche asyncio, toutes les ~10 s, tant que le forward n’est pas fini) : **la même commande**.

`ZADD` sur un membre **déjà présent** ne crée pas de doublon. Redis **remplace le score**. On recule l’expiration de 30 s. `ZCARD` ne change pas.

Un WhisperX de 5 min : ~30 `ZADD`. Le membre reste. `load` ne baisse pas. C’est voulu.

**Sortie normale** (`release` : succès, erreur provider, disconnect FastAPI) :

1. Annuler la tâche asyncio (plus de `ZADD`).
2. `ZREM` le `request_id`. `load` = nouveau `ZCARD`.

On ne « laisse pas expirer » une requête qu’on peut retirer proprement.

##### Frise : la requête va jusqu’au bout

```
t=0      Lua admit : ZADD score=now+30s, membre=R
         start forward + start tâche heartbeat
t=10s    heartbeat : ZADD score=now+30s    (même membre, nouveau score)
t=20s    heartbeat : ZADD score=now+30s
t=30s    heartbeat : ZADD score=now+30s
  …
t=5min   forward OK → cancel tâche → ZREM R
         load a diminué tout de suite
```

##### Frise : le worker crash au milieu

```
t=0      ZADD score=now+30s
t=10s    ZADD score=now+30s
t=12s    SIGKILL / OOM / kill du pod
         plus de tâche, plus de ZADD, plus de ZREM
t=12s…   R est encore dans la ZSET → load trop haut (charge fantôme)
t=12s+30s  le score de R passe dans le passé
           Redis ne fait toujours rien
t=…      une autre requête appelle le Lua d’admission
         purge → ZREM R → load redescend
```

Fenêtre fantôme : **au plus ~30 s** après le crash, pas « jusqu’au prochain redémarrage ». Assez court pour ne pas figer le QoS, assez long pour qu’un heartbeat Redis raté une fois ne tue pas une requête encore vivante (~3 retry si le redis n'est pas disponible / saturé).

| | Intervalle | Expiration | Marge |
|---|---|---|---|
| In-flight | ~10 s | ~30 s | ~3 rappels |

Si le **client** coupe : FastAPI voit le disconnect → `ZREM` **immédiat**. Que « le heartbeat cesse » n’est le chemin que si on n’a pas cet événement (kill brutal du worker, Redis mort au `ZREM`).

##### Purge : `ZRANGEBYSCORE`

Redis ne supprime pas les membres expirés. Le Lua d’admission, **avant** de lire `ZCARD` et de décider d’admettre, demande : « qui a un score déjà dans le passé ? »

* `ZRANGE` = les n premiers (par **rang**).
* `ZRANGEBYSCORE` = les membres dont le **score est dans un intervalle**.

Ici le score *est* la date d’expiration, donc :

```
ZRANGEBYSCORE ogl_qos:load:{provider_id}  -inf  {now_ms}
```

= tous les `request_id` dont l’expiration est **déjà passée**. Puis on les `ZREM` (ou `ZREMRANGEBYSCORE`). Ensuite seulement : `load(p) = ZCARD`.

Sans cette purge, un zombie resterait : `load` trop haut, on refuserait des requêtes alors que le GPU est libre.

##### Deux requêtes qui purgent « en même temps »

Redis exécute les commandes et les scripts Lua **une par une** (un thread). Deux admissions ne s’entrelacent jamais :

1. A : `ZRANGEBYSCORE` → `[R]` ; `ZREM R` ; `ZCARD` ; éventuellement admet.
2. B démarre : `ZRANGEBYSCORE` → `[]` ; rien à retirer ; `ZCARD` déjà juste.

Le `ZREM` d’un membre déjà parti est un no-op. Pas de « double suppression » dangereuse sur la ZSET.

Le conflit *existerait* avec un entier `load` à côté, décrémenté en Python en deux round-trips : A et B liraient les mêmes zombies, puis décrémenteraient chacun → `load` trop bas → sur-admission. Pour `inflight`, `load` **est** le `ZCARD` après purge dans le **même** Lua : ce bug n’a pas de prise.

D’où : purge + `ZCARD` + admission = **un seul** script, pas trois appels Python.

##### Ce que le heartbeat ne remplace pas

| Événement | Action |
|---|---|
| Forward terminé (succès ou erreur) | `ZREM` immédiat |
| Disconnect client / proxy | `ZREM` immédiat |
| Crash worker / kill | Rien à exécuter → le prochain Lua purge à l’expiration |
| Heartbeat Redis raté une fois | On réessaie ; si plusieurs échecs d’affilée, on **préfère arrêter le forward** plutôt que de garder une charge fantôme indéfinie |

**Ops.** La ZSET n’a pas de TTL de clé → `maxmemory-policy noeviction` (une éviction LRU d’un membre casserait `load`).

### 3. Limite de charge `qos_limit(p)`

La limite de charge `qos_limit(p)` est définie au niveau du provider (dépend de la capacité GPU du provider). Ca valeur dépend du type de métrique de charge `qos_metric` choisie. Dans cet ADR, nous prévoyons qu'un seul type de métrique de charge sera implémenté : `inflight`.

La limite de charge peut être à None, ce qui signifie que le provider n'a pas de limite de charge. Dans ce cas, le provider est considéré comme toujours disponible.
Si la limite de charge est à 0, le provider est considéré comme non disponible.
 
### 4. Admission

Lorsqu'une requête arrive, le système va évaluer les providers disponibles. Un provider est disponible si : `load(p) < qos_limit(p)` ou si `qos_limit(p)` est None.

* Cas 1 : au moins un provider est disponible

  Si au moins un provider est disponible alors le système laisse la main au load balancer pour déterminer le provider sur lequel la requête va être exécutée.
  L'admission va transmettre au load balancer la liste des providers disponibles.

* Cas 2 : aucun provider est disponible

  Si aucun provider est disponible alors la requête est envoyée dans une boucle de retry. Un nombre de retry est défini au niveau du router.
  Entre chaque retry, un délai est défini.

### 5. Load balancer (least-busy)

Une fois l'admission réussie, le load balancer va recevoir la liste des providers disponible.

* Cas 1 : un seul provider est disponible

  Le load balancer va retourner le provider disponible sans aucune autre action.

* Cas 2 : plusieurs providers sont disponibles

  Dans ce cas, il y a 2 cas possibles :

  * Cas 2.1 : le router à définit le load balancer en `shuffle`
    Le load balancer va retourner un provider aléatoire parmis les providers disponibles sans considération de la charge.

  * Cas 2.2 : le router à définit le load balancer en `least-busy`

    Si au moins un provider a n'a pas de limite de charge (None), la charge est mesurée par `min(load(p))`.

    Si tous les providers ont une limite de charge définie (qos_limit(p) > 0), la charge est mesurée par `max(qos_limit(p) - load(p))`.
    Cela ne correspond pas forcément au provider avec le plus petit nombre de requêtes en cours (`load(p)`) mais de celui qui dispose du plus grand espace disponible.

Une fois le provider déterminé, le load balancer va transmettre le provider au système pour qu'il puisse exécuter la requête.

### 6. Health : liveness ≠ saturation

Le endpoint GET /health/models va retourner le statut de chaque provider. Actuellement, ce endpoint utilise le endpoint GET /metrics des providers mais cela
pose des problèmes de performance et de scalabilité.

Nous souhaitons utiliser la métrique de charge `load(p)` pour déterminer le statut de chaque provider dans le endpoint GET /health/models.

* Status RED:

  Si load(p) / qos_limit(p) >= qos_health_thresholds[1] et si qos_limit(p) is not None ou si sonde /v1/models return != 200

* Status ORANGE:

  Si load(p) / qos_limit(p) >= qos_health_thresholds[0] and load(p) / qos_limit(p) < qos_health_thresholds[1] et si qos_limit(p) is not None

* Status GREEN:

  Si load(p) / qos_limit(p) < qos_health_thresholds[0]

Le statut est inversé par rapport à la sémantique actuelle, la couleur indiqué par le endpoint est celle du meilleur provider (si 1 provider est rouge et un autre est vert, le endpoint retournera vert pour un même model)

### 7. Un seul Lua : try_admit

Pour éviter les conflits de concurrence, nous utiliserons un seul Lua pour toutes les opérations de QoS (load balancer, admission, heartbeat, purge).
Un seul Lua : Redis exécute les scripts un par un. Purge + éligibilité + choix + incrément = une opération. Pas de course.

Cette section décrit **le moment où une requête a le droit de démarrer**, et **sur quel provider**. Tout ça se passe dans **un seul script Redis Lua**, pas en Python.

En une phrase : **`try_admit` est le seul endroit qui décide « ça rentre ? » et « sur qui ? »**, de façon atomique, en purgeant les morts d’abord, en refusant ce qui ne rentrera jamais, et en n’utilisant la file **que** quand tout le router est vraiment plein.

#### 7.1 Ce que `try_admit` reçoit

```
(provider_id, qos_limit)*   ← tous les providers du router
request_id                  ← identifiant de cette requête
poids                       ← 1 si inflight
```
Actuellement la request ID est généré lors du formattage la réponse par le ProviderClient. Le ProviderClient cherche d'abord dans la response la request ID (généré par le
l'API du provider). Si elle n'est pas trouvée, le ProviderClient génère une nouvelle request ID.

Dorénavant nous allons toujours générer la request ID avant l'appel au Lua et passer le request ID au ProviderClient dans ProviderRequestForwardingUseCase.
Il ne sera plus nécessaire de chercher la request ID dans la réponse du provider.

#### 7.2 Les 6 étapes, une par une

##### 7.2.1 Purger l’in-flight expiré **de chaque** provider

Avant de lire la charge, on enlève les **zombies** : worker crashé, client parti, heartbeat arrêté.

Pour chaque provider du router :

- `ZREMRANGEBYSCORE` : membres dont l’expiration est passée
- `HDEL` : retirer leurs poids du hash
- retrancher ces poids de `load`

**Pourquoi tous les providers, pas seulement un ?** Le Lua choisit *ensuite* lequel admettre. Il faut une photo **fraîche** de tout le router. Sinon un GPU libre (zombie) serait vu comme plein.

Fenêtre fantôme : au plus ~30 s, pas « jusqu’au reboot ».

##### 7.2.3 Admission

Voir section 4. Admission

##### 7.2.4 Load balancer

Voir section 5. Load balancer (least-busy)

##### 7.2.5 Admettre sur `p*` — toujours dans le même script

- `ZADD` in-flight : membre = `request_id`, score = `now + ttl` (~30 s)
- `HSET` le poids (pour pouvoir le retrancher à la sortie / purge)
- si `audio_bytes` : incrémenter l’entier `load`

Atomique = personne d’autre ne peut « voler » le slot entre le test et l’incrément.

### Annexe 1. `Retry-After`

Paramètres **router** (V1 = deux leviers, pas trois) :

| Paramètre | Rôle |
|---|---|
| `qos_mode` | `off` \| `reject` \| `queue` |
| `qos_wait_timeout` | Obligatoire si `queue`. Durée max de l’attente HTTP **et** dans la ZSET. Doit rester `< min(timeout)` des providers du router (défaut provider 300 s). |
| `max_queue_size` | Cap de `wait:load` dans l’unité de `qos_metric`. `null` = pas de cap. |

`qos_mode` :

| Valeur | Comportement |
|---|---|
| `off` | Pas d’admission. Kill switch. WhisperX n’est **pas** protégé. |
| `reject` | `FULL` → 503 immédiat, pas de ZSET. |
| `queue` | `FULL` → file jusqu’à `qos_wait_timeout`. |

Pas de tri-état `qos_wait_timeout = null` qui signifierait à la fois « pas de file » et « pas de 503 » : le nom se lirait comme « attendre indéfiniment » et désactiverait la protection.

Erreur : **503** + `Retry-After` (secondes). Le header **ne promet pas un slot**.

```
Retry-After = clamp(1, qos_wait_timeout, ceil((1 + depth) * (0.5 + rand())))
```

`depth = ZCARD` si `inflight`, `ceil(wait:load / max(1, poids moyen récent ou poids de la requête))` si `audio_bytes` — en V1, plus simple : `depth = ZCARD` dans les deux cas. Jitter 50 %–150 % anti-stampede. Pas de timeserie `ogl_ts:latency`, pas de p50, pas de « provider de référence ». Un `D × (charge + file + poids) / limite` mélange durée d’une requête et ratio d’octets ; il n’est correct que si `D` est le temps de drainer une capacité pleine, ce que le p50 n’est pas.
