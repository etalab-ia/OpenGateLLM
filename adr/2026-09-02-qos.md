# ADR - 2026-09-02 - Quality of Service (QoS)

* **Status:** Draft
* **Date:** 2026-09-02
* **Authors:** Development Team
* **Related:**
  * ADR à venir — priorisation des requêtes
  * ADR à venir — batch
* **Decision Outcome:** Une charge `load(p)` comptée dans Redis (ZSET + heartbeat), une admission atomique Lua (`try_admit`) qui choisit aussi le provider (`load_balancing_strategy`) et tourne **toujours** (least-busy et health), un health de saturation sur `qos_limit` (RED à `load >= qos_limit`, ORANGE à `load >= 0.95 × qos_limit`, constante code), plafond d’admission via `qos_retries_before_reject` (`None` = pas de plafond, `0` = 503 immédiat, `n > 0` = attente). Métrique unique `inflight` (pas stockée).

---

## Context

Nous voulons **protéger chaque provider**, **envoyer au moins chargé**, et **aligner le health** sur la même source de vérité que l’admission.

Trois besoins product liés, dont seul le second est tranché ici :

1. **Priorisation** — traiter certaines requêtes avant d’autres en période de charge (ADR suivant).
2. **Qualité de service (QoS)** — plafonner la charge admise sur un provider pour :
   * éviter le crash des moteurs fragiles (ex. WhisperX) ;
   * fluidifier ceux qui tiennent la charge mais sont mal calibrés (ex. vLLM) ;
   * exposer un health cohérent **sans** s’appuyer sur l’API métriques du provider.
3. **Batch** — lancer des jobs quand les providers ont de la marge (ADR suivant).

Le batch a besoin d’un indicateur de charge. La priorisation a besoin d’un mécanisme d’attente. Le QoS fournit cet indicateur et l’attente d’admission (boucle dans la requête HTTP), sans file Redis prioritaire.

**Hors périmètre de cet ADR**

* Priorisation entre requêtes (files ordonnées, poids utilisateur / clé).
* Batch / exécution différée.
* Métriques de charge autres que `inflight` (tokens in-flight, audio bytes, …) — voir suivi : la métrique restera **unique**, pas configurable par router / provider.
* Migration depuis Celery / RabbitMQ / compteur `ogl_mg:inflight` (feuille blanche volontaire).

---

## Decision

### 1. Une source de charge, trois consommateurs

On compte **nous-mêmes** dans Redis. Pas d’API métriques provider pour l’admission, le least-busy, ni la **saturation** health.

Aujourd’hui le QoS et le least-busy lisent un compteur Redis (`ogl_mg:inflight`) que l’on incrémente au début de la requête et décrémente à la fin (`INCR` / `DECR`). Le **contrôle de limite** et l’**incrément** sont deux allers-retours distincts : deux requêtes peuvent toutes les deux voir « il reste de la place » et entrer. Un crash laisse le compteur trop haut indéfiniment.

On remplace ce système par un seul nombre `load(p)` (voir §2) (charge actuelle du provider `p`) et une limite `qos_limit(p)` (voir §3) :

| Mécanisme | Question | Condition |
| --- | --- | --- |
| Admission | Cette requête peut-elle **démarrer** sur au moins un provider sans dépasser sa capacité ? | Si `qos_retries_before_reject is None` : oui dès qu’un provider n’est pas fermé (`qos_limit ≠ 0`), quitte à dépasser `qos_limit` (voir §4.1). Sinon : il existe un `p` éligible : `qos_limit(p) is None` **ou** `load(p) < qos_limit(p)` (voir §4) |
| Load balancer | Parmi les éligibles, lequel prend la requête ? | `shuffle` ou `least_busy` via `load_balancing_strategy` (voir §5) |
| Saturation health (`GET /health/models`) | À quel point `p` est-il **plein** ? | `load(p)` comparé à `qos_limit(p)` : RED si `load >= qos_limit`, ORANGE si `load >= 0.95 × qos_limit` (voir §6) |

Admission, choix du provider et réservation du slot se font dans **le même** script Lua (`try_admit`, §7), **y compris** quand le plafond d’admission est désactivé (`qos_retries_before_reject is None`) : sans `ZADD`, ni least-busy ni health n’auraient de charge. Le heartbeat et le `release` sont des commandes Redis séparées (pas un second `try_admit`).

### 2. Métrique de charge `load(p)` (`inflight`)

Chaque provider a **une** ZSET Redis `ogl_qos:load:{provider_id}`. `load(p)` est le `ZCARD` de cette ZSET **après** purge des membres expirés. On ne tient **pas** d’entier `INCR` / `DECR` à côté : ce second chiffre divergerait (crash, `DECR` perdu). Compter les membres *est* la charge.

#### 2.1 Type de métrique

La métrique est **unique** pour tous les providers : pas de champ `qos_metric` en base, pas de réglage par router ni par provider.

Cet ADR spécifie `inflight` (chaque requête pèse 1). Une évolution ultérieure pourra remplacer `inflight` par une métrique à **poids variable** (tokens in-flight, audio bytes, …) — toujours unique, toujours la même unité partout. `qos_limit` s’exprime dans cette unité.

Pour `inflight` :

* **membre** = `request_id` : une requête encore en cours ;
* **score** = date d’expiration du heartbeat (millisecondes Unix), **pas** un rang dans une file ;
* **`load(p)`** = `ZCARD` après retrait des membres expirés.

#### 2.2 Heartbeat in-flight

##### Le problème

Sans filet, un crash worker, un Redis saturé au `DECR` / `ZREM`, ou un `finally` qui ne tourne pas laisse la charge trop haute indéfiniment. On sous-admet alors que le GPU est libre.

Il faut un filet qui n’exige **aucun code après la mort** du process.

##### L’idée

Tant que *cette* requête vit, le worker qui la sert **recule une date d’expiration** sur le membre (heartbeat). Si les rappels s’arrêtent, la date passe dans le passé. Redis **n’efface rien tout seul** : le prochain `try_admit` purge les scores dépassés avant de lire `ZCARD`.

Ce n’est **pas** :

* Redis qui « ping » tout seul ;
* un cron, un worker Celery, un sweeper dédié ;
* un `EXPIRE` sur la clé ZSET (un TTL de clé détruirait **toutes** les requêtes du provider d’un coup) ;
* une mesure de la durée du job (un WhisperX de 5 min doit rester dans `load` jusqu’à la fin).

C’est uniquement le filet anti-zombie. La sortie **normale** retire le membre tout de suite (`ZREM`), sans attendre les ~30 s.

##### Qui

Le **même process FastAPI** (worker gunicorn / uvicorn) qui traite **cette** requête HTTP.

Au moment où l’admission réussit, l’adapter Redis démarre une **tâche asyncio** à côté de l’`await forward_request(...)`. Cette tâche vit aussi longtemps que le forward.

```
requête HTTP
  └─ worker FastAPI
       ├─ await forward_request(...)     # peut durer des minutes
       └─ tâche asyncio heartbeat        # toutes les ~10 s : ZADD, jusqu’à la fin du forward
```

##### Quoi, dans Redis

```
ZSET  ogl_qos:load:{provider_id}

  membre = request_id          # quelle requête
  score  = now_ms + 30_000     # morte si plus personne n’écrit d’ici 30 s
```

Exemple, trois requêtes sur le provider 42, `now = 1_000_000` :

| membre | score | lecture |
|---|---|---|
| `req-A` | `1_028_000` | encore 28 s de silence autorisé |
| `req-B` | `1_015_000` | encore 15 s |
| `req-C` | `980_000` | **déjà expiré** (score &lt; now) → zombie à purger |

`load(p)` n’est pas « 3 » tant qu’on n’a pas enlevé `req-C`. Après purge : `ZCARD` = 2.

##### Comment on écrit

**Admission** (dans `try_admit`, une fois) :

```
ZADD ogl_qos:load:{provider_id}  {now_ms + 30_000}  {request_id}
```

**Heartbeat** (tâche asyncio, toutes les ~10 s) : **la même commande**, avec `XX` (ne pas recréer un membre déjà `ZREM`). Chaque tick : jusqu’à **3** tentatives Redis ; si les 3 échouent → tenter un `ZREM` (purge de ce membre) et **poursuivre le forward** (voir tableau ci-dessous). `ZCARD` ne change pas sur un refresh réussi.

**Sortie normale** (`release` : succès, erreur provider, disconnect client vu par FastAPI) :

1. Annuler la tâche asyncio (plus de `ZADD`).
2. `ZREM` le `request_id`.

On ne « laisse pas expirer » une requête qu’on peut retirer proprement.

##### Frise : la requête va jusqu’au bout

```
t=0      try_admit : ZADD score=now+30s, membre=R
         start forward + start tâche heartbeat
t=10s    heartbeat : ZADD score=now+30s
t=20s    heartbeat : ZADD score=now+30s
  …
t=5min   forward OK → cancel tâche → ZREM R
         load a diminué tout de suite
```

##### Frise : le worker crash au milieu

```
t=0      ZADD score=now+30s
t=10s    ZADD score=now+30s
t=12s    SIGKILL / OOM / kill du pod
         plus de ZADD, plus de ZREM
t=12s…   R est encore dans la ZSET → charge fantôme
t=12s+30s  le score de R passe dans le passé
t=…      une autre requête appelle try_admit
         purge → ZREM R → load redescend
```

Fenêtre fantôme : **au plus ~30 s** après le crash. Assez court pour ne pas figer le QoS, assez long pour qu’un heartbeat Redis raté **une** fois ne tue pas une requête encore vivante (~3 retries).

| | Intervalle | Expiration | Marge |
|---|---|---|---|
| In-flight | ~10 s | ~30 s | ~3 rappels |

Si le **client** coupe : FastAPI voit `is_disconnected` → annuler le forward + `ZREM` **immédiat**. Que « le heartbeat cesse » n’est le chemin que si on n’a pas cet événement (kill brutal du worker, Redis mort au `ZREM`).

##### Purge : `ZRANGEBYSCORE` / `ZREMRANGEBYSCORE`

Le score *est* la date d’expiration :

```
ZREMRANGEBYSCORE ogl_qos:load:{provider_id}  -inf  {now_ms}
```

Puis seulement : `load(p) = ZCARD`.

##### Concurrence

Redis exécute scripts Lua et commandes **un par un**. Deux `try_admit` ne s’entrelacent jamais : purge + `ZCARD` + décision + `ZADD` = **un seul** script. Le conflit d’un entier `load` lu puis décrémenté en Python (deux round-trips) n’a pas de prise ici.

##### Ce que le heartbeat ne remplace pas

| Événement | Action |
|---|---|
| Forward terminé (succès ou erreur) | `ZREM` immédiat |
| `request.is_disconnected` (client / proxy) | Annuler le forward + `ZREM` immédiat |
| Crash worker / kill | Rien à exécuter → le prochain `try_admit` purge à l’expiration |
| Heartbeat Redis : 3 essais échoués sur un tick | Tenter `ZREM` de ce `request_id` ; **arrêter la tâche heartbeat** ; **ne pas** annuler le forward (panne Redis ≠ panne provider). Sur-admission possible tant que le forward tourne. Si le `ZREM` échoue aussi, expiration via le prochain `try_admit` (~30 s) |

**Ops.** La ZSET n’a pas de TTL de clé → `maxmemory-policy noeviction` (une éviction LRU d’un membre casserait `load`).

##### `request_id`

Généré **avant** l’appel à `try_admit` (UUID), passé au `ProviderClient` par le use case de forward. On ne lit plus d’id dans la réponse provider pour le QoS : le membre Redis doit exister dès l’admission, avant tout octet provider.

### 3. Limite de charge `qos_limit(p)`

`qos_limit(p)` est définie **au niveau du provider** (capacité GPU / calibre du moteur). Unité V1 (`inflight`) : entier = nombre max de requêtes concurrentes. Quand la métrique unique passera à un poids variable, `qos_limit` s’exprimera dans cette unité.

Pas de champ `qos_limit_orange` ni de `qos_health_thresholds` : le seuil ORANGE est dérivé en code, `0.95 × qos_limit` (voir §6).

| Valeur | Sens |
|---|---|
| `None` | Pas de plafond d’admission, pas de RED / ORANGE de saturation. Le provider est toujours éligible (sous réserve de la sonde health, §6). |
| `0` | Provider fermé : jamais éligible (y compris si `qos_retries_before_reject is None`) → RED. |
| `n > 0` | Au plus `n` requêtes concurrentes **lorsque le plafond d’admission est actif** (`qos_retries_before_reject is not None`). `load` atteint `n` ⇒ plus éligible. Si le plafond est inactif, `n` sert au health et au least-busy, pas à bloquer. |

### 4. Admission

À l’arrivée d’une requête, `try_admit` évalue les providers du router. Le script tourne **toujours** (pas de kill switch qui skip l’admission).

Un provider est **éligible** si et seulement si :

* `qos_limit(p) is None`, **ou**
* `qos_limit(p) > 0` et (`qos_retries_before_reject is None` **ou** `load(p) < qos_limit(p)`).

(`qos_limit(p) == 0` : jamais éligible.)

(Inégalité stricte quand le plafond est actif : avec `qos_limit = 2`, on admet quand `load` vaut 0 ou 1 ; après deux admissions réussies `load = 2`, plus d’admission. Capacité max = `qos_limit`.)

* **Cas 1 — au moins un provider éligible**

  Le script enchaîne le load balancer (§5) sur **cette** liste d’éligibles, réserve le slot (`ZADD`), renvoie `ADMITTED, p*`.

* **Cas 2 — aucun provider éligible**

  Le script renvoie `FULL` (pas de `ZADD`). Le comportement HTTP dépend de `qos_retries_before_reject` (§4.1).

  Avec `qos_retries_before_reject is None`, `FULL` n’arrive que si tous les providers sont fermés (`qos_limit == 0`) : la sur-admission rend les autres toujours éligibles.

#### 4.1 Comportement quand le router est plein (`qos_retries_before_reject`)

Pas de champ `qos_mode`. Un seul paramètre router, `qos_retries_before_reject` (`int ≥ 0` \| `None`).

`try_admit` tourne dans tous les cas : choix du provider, `ZADD`, heartbeat — pour alimenter least-busy et le health de saturation.

| Valeur | Effet |
|---|---|
| `None` (défaut) | Pas de plafond d’admission : `try_admit` choisit un provider et réserve le slot même si `load(p) >= qos_limit(p)` (sur-admission). `qos_limit` sert au health et au least-busy, pas à bloquer. Si tous les providers sont fermés (`qos_limit == 0`) → `FULL` → **503**. |
| `0` | Premier `FULL` → **503** immédiat + `Retry-After` (équivalent de l’ancien mode `reject`, volontairement non introduit). |
| `n > 0` | `FULL` → boucle dans la requête HTTP : sleep **0,5 s** (constante code, non configurable) puis rappel de `try_admit`, au plus `n` fois. Après épuisement → **503** + `Retry-After` (annexe). Durée max d’attente ≈ `n × 0,5` s. |

`None` et `0` sont deux comportements distincts : pas de protection vs rejet immédiat.

Ce n’est **pas** une file Redis partagée : chaque requête HTTP poll indépendamment. L’ordre d’admission sous contention n’est pas garanti (FIFO non promis). Une file ordonnée / prioritaire est hors périmètre (ADR priorisation).

### 5. Load balancer

Champ router déjà existant : `load_balancing_strategy` (`RouterLoadBalancingStrategy` : `shuffle` \| `least_busy`).

Une fois la liste des éligibles connue **dans** `try_admit`, le script choisit `p*` selon cette stratégie.

* **Un seul éligible** → ce provider.
* **Plusieurs éligibles** :
  * `shuffle` — un provider tiré au hasard parmi les éligibles (sans regarder `load`).
  * `least_busy` :
    * si **au moins un** éligible a `qos_limit is None` : choisir `argmin load(p)` parmi les éligibles (les `None` et les plafonnés sont comparés sur `load` brut) ;
    * si **tous** les éligibles ont un `qos_limit > 0` : choisir `argmax (qos_limit(p) - load(p))` (plus grand **espace restant**, pas forcément le plus petit `load`). L’espace restant peut être **négatif** en sur-admission (`qos_retries_before_reject is None`) : on envoie vers le moins dépassé.

En cas d’égalité (même `load` ou même espace restant) : départage déterministe dans le Lua (ex. plus petit `provider_id`) pour éviter le brassage inutile entre appels.

Le use case forward **sur `p*` renvoyé par le script** — pas un second passage load balancer en Python.

### 6. Health : liveness ≠ saturation

`GET /health/models` expose le statut de chaque provider. La **saturation** compare `load(p)` (même Redis que l’admission) à `qos_limit(p)`, pas `GET /metrics` du provider.

La **liveness** reste une sonde séparée, déclenchée **uniquement** lors de l’appel à `GET /health/models` (comme aujourd’hui) : typiquement `GET /v1/models` du provider, **timeout 4 s**, **pas de cache en V1**. Un provider peut être vert en saturation et rouge en liveness, ou l’inverse.

#### 6.1 Statut de saturation d’un provider

Seuil ORANGE dérivé, constante code, **comparaison flottante** (pas d’arrondi, pas de champ persisté) :

```
orange_limit = 0.95 * qos_limit    # uniquement si qos_limit > 0
```

Évaluation dans cet ordre (RED gagne sur ORANGE) :

| Statut | Condition |
|---|---|
| **RED** | Liveness en échec **ou** `qos_limit(p) == 0` **ou** (`qos_limit(p) > 0` et `load(p) >= qos_limit(p)`) |
| **ORANGE** | Liveness OK, pas RED, `qos_limit(p) > 0`, et `load(p) >= 0.95 * qos_limit(p)` |
| **GREEN** | Liveness OK, et ni ORANGE ni RED |

Orange = warning **avant** le cap ; rouge = le cap. À `load == qos_limit` le provider est **RED**. Avec le plafond d’admission actif, `load` plafonne à `qos_limit` donc le RED de saturation est atteint pile à saturation ; en sur-admission (`qos_retries_before_reject is None`) `load` peut dépasser `qos_limit` et reste RED.

V1 `inflight` : `load` et `qos_limit` sont des entiers. ORANGE n’est visible que s’il existe un entier `k` tel que `0.95 × qos_limit ≤ k < qos_limit`, donc seulement si **`qos_limit ≥ 20`**. En dessous (1, 2, 4, 8, …) on passe de GREEN à RED, sans ORANGE. Pas d’arrondi pour inventer une bande : le 0,95 est strict. Une métrique à poids (suivi) rendra la bande utile aussi pour les petites capacités.

#### 6.2 Agrégation par modèle / router

Pour un même modèle exposé via plusieurs providers, la couleur renvoyée par l’endpoint est celle du **meilleur** provider (vert > orange > rouge). Un provider rouge n’assombrit pas le modèle si un autre est vert.

*(Note : c’est l’inverse d’une sémantique « le pire maillon » ; à documenter côté ops / monitoring.)*

### 7. Un seul Lua d’admission : `try_admit`

`try_admit` est le **seul** endroit qui décide atomiquement « ça rentre ? » et « sur qui ? » : purge → éligibles → choix → `ZADD`.

Le heartbeat (`ZADD` périodique) et le `release` (`ZREM`) sont des commandes hors script, sur la même ZSET.

#### 7.1 Entrées

```
(provider_id, qos_limit)*   ← tous les providers du router
request_id                  ← UUID généré avant l’appel
strategy                    ← load_balancing_strategy du router (shuffle | least_busy)
enforce_limit               ← true ssi qos_retries_before_reject is not None
now_ms                      ← horloge du serveur Redis (TIME) de préférence, pour éviter le skew multi-worker
```

Le seuil ORANGE n’entre pas dans le Lua (affichage health uniquement, hors script).

V1 `inflight` : pas de poids variable (chaque admission = +1 membre).

#### 7.2 Étapes

##### 7.2.1 Purger l’in-flight expiré **de chaque** provider

Pour chaque provider du router : `ZREMRANGEBYSCORE … -inf now_ms`. Photo fraîche de tout le router avant le choix.

##### 7.2.2 Trop lourd → `TOO_HEAVY` (413)

**Non implémenté en V1.** Réservé au jour où la métrique unique passera à un poids variable (tokens, audio bytes, …) et qu’une seule requête pourra dépasser `qos_limit`.

##### 7.2.3 Éligibilité

Comme §4 (`enforce_limit` pilote le filtre `load < qos_limit`). Si vide → retourner `FULL` (pas de `ZADD`).

##### 7.2.4 Load balancer

Comme §5, **dans** le script, sur la liste d’éligibles → `p*`.

##### 7.2.5 Réserver le slot sur `p*`

```
ZADD ogl_qos:load:{p*}  {now_ms + 30_000}  {request_id}
```

Sans cette écriture dans le même script, deux workers pourraient tous deux voir une place libre et dépasser `qos_limit` (quand `enforce_limit`).

##### 7.2.6 Retour

`ADMITTED, p*` — le use case forward uniquement sur ce provider.

## Consequences

### Positives

* Une seule source de vérité pour admission, least-busy et saturation health — `try_admit` tourne même sans plafond, donc le compteur Redis reste alimenté.
* Plus de course « check puis incrément » : le slot est réservé atomiquement.
* Charge fantôme bornée (~30 s) sans sweeper dédié.
* Un seul champ `qos_retries_before_reject` (`None` / `0` / `n`) pour le comportement sous saturation, sans `qos_mode` ni mode `reject` redondant.
* Health de saturation scalable (Redis) sans fan-out `/metrics` provider.
* Un seul champ provider `qos_limit` : pas de `qos_limit_orange`, pas de `qos_health_thresholds` ; l’ORANGE est `0.95 × qos_limit` en code.
* Métrique unique non persistée : pas de colonne / enum `qos_metric` à faire diverger entre routers.

### Négatives / coûts

* Dépendance forte à Redis (dispo, `noeviction`, latence) sur le chemin critique d’admission — y compris quand le plafond est `None` (least-busy / health).
* `qos_retries_before_reject > 0` = polling dans la requête : connexions HTTP occupées, pas de FIFO global, stampede possible à la libération d’un slot (atténué par le sleep fixe 0,5 s + jitter `Retry-After` côté 503).
* Fenêtre fantôme jusqu’à ~30 s après un crash : sous-admission temporaire.
* Heartbeat Redis en échec → on **retire** éventuellement la requête de `load` tout en laissant le forward tourner : risque de **sur-admission** temporaire (choix conscient : ne pas tuer le provider pour une panne Redis).
* Heartbeat asyncio par requête longue : coût CPU / connexions Redis à dimensionner.
* Agrégation health « meilleur provider » peut masquer un replica rouge.
* `qos_limit is None` = pas de plafond d’admission ni de couleur de saturation sur ce provider ; `qos_retries_before_reject is None` = pas de plafond d’admission sur le router (sur-admission possible, health et least-busy restent justes).
* À saturation (`load == qos_limit`) le provider est RED.
* V1 `inflight` : pas d’ORANGE si `qos_limit < 20` (aucun entier entre `0.95 × n` et `n`). Accepté.

### Suivi

* ADR priorisation : file Redis ordonnée, caps de file, interaction avec `qos_retries_before_reject`.
* ADR batch : consommation de `load(p)` / health pour déclencher les jobs.
* Évolution de la métrique unique : poids variables (toujours la même unité pour tous les providers), étape `TOO_HEAVY`, éventuellement hash de poids à côté de la ZSET. La bande ORANGE `0.95 × qos_limit` devient alors visible aussi pour les petites capacités.

## Configuration (synthèse V1)

| Paramètre | Type | Défaut | Scope |
|---|---|---|---|
| `qos_limit` | int \| None | `None` | Provider |
| `qos_retries_before_reject` | int (≥ 0) \| None | `None` | Router |
| `load_balancing_strategy` | `shuffle` \| `least_busy` | (existant) | Router |

Pas de `qos_metric`, `qos_mode`, `qos_limit_orange`, ni `qos_health_thresholds` : métrique unique `inflight` (code), plafond d’admission router via `qos_retries_before_reject`, ORANGE = `0.95 × qos_limit` (code).

Constantes **code** (non configurables par router / provider en V1) :

| Constante | Valeur |
|---|---|
| Métrique de charge | `inflight` |
| Seuil ORANGE | `0.95 × qos_limit` (comparaison flottante) |
| Délai entre deux `try_admit` si `qos_retries_before_reject > 0` | `0.5` s |
| Intervalle heartbeat | ~10 s |
| TTL score heartbeat | ~30 s |
| Retries Redis par tick heartbeat | `3` |
| Timeout sonde liveness (`GET /v1/models`) | `4` s |

## Annexe — `Retry-After` (réponses 503)

Quand l’admission échoue de façon terminale (`qos_retries_before_reject` n’est pas `None` et est épuisé, y compris `0` dès le premier `FULL` ; ou tous les providers fermés), réponse **503** + header `Retry-After` (secondes). Le header **ne promet pas un slot**.

```
plafond = max(1, ceil(qos_retries_before_reject * 0.5))   # durée max d’attente déjà consentie ; si 0 → 1
Retry-After = clamp(1, plafond, ceil((1 + depth) * (0.5 + rand())))
```

Si `qos_retries_before_reject is None` (503 uniquement si tous les providers sont fermés) : `plafond = 1`.

* `depth` = somme des `ZCARD` des ZSET `load` des providers du router (approximation de la profondeur de saturation).
* Jitter 50 %–150 % anti-stampede.
* Pas de timeserie de latence, pas de p50 provider : trop fragile et hors besoin V1.
* Pas de mode `reject` : le cas « 503 immédiat » est `qos_retries_before_reject = 0` ; le plafond `Retry-After` reste défini (`1` s min via la formule ci-dessus).
